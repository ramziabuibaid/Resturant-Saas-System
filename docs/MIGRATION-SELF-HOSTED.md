# النقل إلى سيرفر محلي والاستغناء عن Supabase

> تاريخ الفحص: 2026-10-30 · تأتي هذه الخطة **قبل** المرحلة 1 (التصميم)، حتى لا نعيد كتابة نفس الكود مرتين.

## 1. اختيار السيرفر

| | homeserver | storeserver ✅ |
|---|---|---|
| المعالج | i5-10500 · 12 خيط | i5-6500 · 4 أنوية |
| الذاكرة | 14GB — **مستخدم 8.8GB + 2.4GB swap** (ضغط) | 14GB — مستخدم 2.4GB، **متاح 12GB** |
| القرص | **88% ممتلئ** (28GB متبقية) | 9% (202GB متبقية) |
| الحمل الحالي | Supabase ×2 (31 حاوية)، بريد، n8n، بوتات تداول | Supabase واحد + bazarko فقط |
| النشر للإنترنت | — | **Cloudflare Tunnel جاهز** (يخدم `*.bazarko.app` بنفس فكرة المطاعم) |

**القرار: storeserver.** المعالج أقدم لكنه أكثر من كافٍ لهذا التطبيق، والذاكرة والقرص فارغان تقريباً، وطريقة النشر نفسها مجرّبة عليه مع bazarko.

> ⚠️ **تنبيه:** إذا انقطع الإنترنت أو الكهرباء في المحل يتوقف منيو كل المطاعم. يوجد UPS (خدمة NUT تعمل)، لكن يُفضّل لاحقاً نسخة احتياطية يومية خارج السيرفر.

## 2. البنية الجديدة

```
الإنترنت → Cloudflare (resturant.app و *.resturant.app)
         → Cloudflare Tunnel على storeserver
         → حاوية app (Next.js، منفذ 3100 محلي فقط)
         → حاوية db  (PostgreSQL 17، داخل شبكة Docker فقط، بلا منفذ خارجي)
         → مجلد uploads/ للصور (على القرص)
```

كله في `docker-compose.yml` واحد ومستقل تماماً عن Supabase الخاص بـ bazarko.

| الآن (Supabase) | بعد النقل |
|---|---|
| Postgres + RLS | PostgreSQL 17 عادي + **Drizzle ORM** (أنواع TypeScript تلقائية) |
| Supabase Auth | جلسات خاصة بنا: جدول `users` + `sessions`، كلمات مرور مشفّرة (argon2)، كوكي httpOnly |
| Supabase Storage | مجلد `uploads/` على القرص، يُقدَّم عبر route في Next.js |
| Realtime (جرس الطلبات) | استعلام دوري كل بضع ثوانٍ (أبسط وكافٍ) |
| دوال RPC (6 دوال) | معاملات (transactions) في TypeScript |
| RLS | **كل الصلاحيات في الخادم**: دالة واحدة تعيد مطعم المستخدم، وكل استعلام مقيّد بـ `restaurant_id` |

## 3. حجم العمل

- 180 استعلام `.from()` في نحو 3,900 سطر (`src/app/actions/` و `src/lib/`).
- نحو 20 استدعاء Auth، و8 للتخزين، ومكوّن Realtime واحد، و6 دوال RPC.
- قاعدة بيانات **جديدة ونظيفة**: لا نقل بيانات من Supabase. نوحّد جداول الولاء المكررة
  (`restaurant_customer_phones` القديم + الجداول الجديدة) في تصميم واحد.

## 5. المطلوب منك (فقط عند الخطوة M7–M8، ليس الآن)

1. **نقل DNS لـ `resturant.app` إلى Cloudflare.** حالياً هو على Vercel DNS، والـ Tunnel يحتاج Cloudflare.
   تضيف الدومين في حساب Cloudflare (نفس حساب bazarko)، ثم تغيّر الـ nameservers عند مسجّل الدومين.
2. **صلاحية sudo مرة واحدة** لإضافة الدومين إلى ملف الـ Tunnel، أو أنشئ Tunnel جديداً من لوحة Cloudflare وأعطني الـ token في ملف على السيرفر.

كل ما قبل ذلك أنفّذه وحدي.

## سجل التنفيذ

### M1 ✅ (2026-10-30)
- قاعدة تطوير محلية: PostgreSQL 17 في `.pgdata/` على المنفذ 5442 — `npm run db:start` / `db:stop` / `db:psql`.
  (Docker غير مثبت على الجهاز؛ على السيرفر سنستخدم Docker في M7.)
- المخطط: [`src/db/schema.ts`](../src/db/schema.ts) — 15 جدولاً. الـ migration: `drizzle/0000_init.sql`.
- الاتصال: [`src/db/index.ts`](../src/db/index.ts) (`db` من drizzle-orm + postgres.js).
- فحص: `npm run db:smoke` (ينشئ بيانات داخل معاملة ثم يتراجع).

**قرارات في المخطط:**
- `users` + `sessions` بدل Supabase Auth و `profiles`. اسم المستخدم فريد داخل المطعم.
- `customers` يدمج `customer_profiles` + `restaurant_customer_phones` + `loyalty_accounts`.
- `loyalty_transactions` يدمج السجلّين القديمين، مع منع منح نقاط الطلب مرتين (فهرس فريد).
- `restaurants.last_order_number` بدل جدول العدادات.
- `order_items.item_name` يحفظ اسم الصنف وقت الطلب، فحذف الصنف لاحقاً لا يكسر الطلبات القديمة.
- الحالات والأنواع enums في Postgres (`order_status`، `user_role`، ...) بدل نص حر.
- مطعم جديد يبدأ بحالة `trial` والعملة الافتراضية `ILS`.

### M2 ✅ (2026-10-30)
- **كلمات المرور:** `scrypt` المدمج في Node (بلا مكتبات) — [`src/lib/auth/password.ts`](../src/lib/auth/password.ts).
- **الجلسات:** رمز عشوائي في كوكي `rs_session` (httpOnly)، والقاعدة تحفظ SHA-256 له فقط، صلاحية 30 يوماً.
  الكوكي مربوط بالنطاق: جلسة `demo.example.com` لا تعمل على مطعم آخر — [`src/lib/auth/session.ts`](../src/lib/auth/session.ts).
- **من المستخدم الحالي:** [`src/lib/auth/current-user.ts`](../src/lib/auth/current-user.ts) (يعيد `Profile` بنفس الشكل القديم).
- **قراءات المطاعم:** [`src/lib/data/restaurants.ts`](../src/lib/data/restaurants.ts) — خارج `"use server"` عمداً.
- **محوَّل بالكامل:** الدخول (بريد / اسم مستخدم / صاحب مطعم)، التسجيل، إنشاء المطعم، الخروج، الـ proxy،
  `api/resolve-tenant`، لوحة Super Admin (الإحصائيات، إنشاء/حذف مطعم، تغيير النطاق، بيانات دخول المالك).
- **حُذف:** صفحة استعادة كلمة المرور بالبريد ومسار `auth/callback` (كانا لـ Supabase). البديل الآن:
  مالك النظام يغيّر كلمة مرور المالك من لوحته، و `npm run user:password -- <email|username>` من سطر الأوامر.
- **البذرة:** `npm run db:seed` ← مالك النظام `admin@resturant.app` + مطعم «مطعم الديوان» (`demo`) بمنيو وصور و6 طاولات.
  كلمات المرور المولّدة في `.seed-credentials.local` (خارج git).
- **اختُبر في المتصفح:** كلمة مرور خاطئة تُرفض، دخول صاحب المطعم، دخول مالك النظام، الخروج ينهي الجلسة،
  تسجيل حساب جديد → إنشاء مطعم → لوحته، رفض نطاق مستخدم.

**حالة الفرع:** الدخول واللوحتان الرئيسيتان تعمل على Postgres. باقي الصفحات (المنيو، الطلبات، الإعدادات…)
ما زالت تقرأ من Supabase حتى M3–M6، لذلك لا يُدمج هذا الفرع في `main` قبل انتهاء M6.

### M3 ✅ (2026-10-30)
- **قراءات المنيو:** [`src/lib/data/menu.ts`](../src/lib/data/menu.ts) (حُذف `src/app/actions/menu.ts` — كان كله قراءات مكشوفة).
- **التصنيفات والأصناف والإعدادات:** المطعم يُؤخذ من الجلسة دائماً؛ معرّف المطعم القادم من المتصفح يُتجاهل.

- **الرفع (نُقل من M6):** `POST /api/uploads` ← `uploads/{restaurantId}/{uuid}.{ext}`، ويُقدَّم من `/uploads/...`.
  نوع الملف يُكشف من محتواه (SVG مرفوض)، حدود الحجم: صورة صنف 5MB، شعار 2MB، بانر/فيديو 30MB.
- **اختُبر:** المنيو العام بالصور والأحجام، إضافة/حذف تصنيف، إيقاف/تفعيل صنف، حفظ الإعدادات، رفع صورة صحيحة،
  رفض SVG متنكّر، رفض بلا جلسة، رفض الحجم الزائد، طلبات Range للفيديو، ومحاولات تجاوز المسار.

**ما زال على Supabase:** الطاولات، النُدُل، الطلبات، الزبائن والولاء، الإشعارات (M4–M6).

### M4 ✅ (2026-10-30)
- **الطاولات والنُدُل والطلبات** على Postgres. قراءات الطاولات العامة في [`src/lib/data/tables.ts`](../src/lib/data/tables.ts).
- **إنشاء الطلب في معاملة واحدة:** رقم الطلب، الزبون، البنود، وخصم النقاط — إما كلها أو لا شيء.

- **حد للطلبات:** 10 طلبات / 10 دقائق لكل جهاز ومطعم، و30 معاينة نقاط / دقيقة ([`src/lib/rate-limit.ts`](../src/lib/rate-limit.ts)).

  إعادة «مكتمل» لا تضاعف النقاط، طلب ثانٍ بخصم 100 نقطة (₪10)، صفحة التتبع، الجرس التقط طلباً جديداً.

- **خلل قديم أُصلح:** 3 نماذج في لوحة الولاء (حفظ مكافأة، استبدال سريع، استبدال مكافأة) لم تكن تعمل أصلاً —

- **اختُبر:** صفحة العملاء، حفظ مكافأة من الواجهة، استبدال مكافأة ثم رفض الثانية (نفد المخزون)، استبدال نقدي أكبر من الرصيد

- ⚠️ **الإشعارات ما زالت محاكاة:** زر «تشغيل المعالج» يعلّم الرسائل «sent» دون إرسال فعلي — لا يوجد مزود SMS/واتساب بعد.

**بعد M5 لا يستورد أي ملف في التطبيق Supabase.** المتبقي في M6: حذف الحزم والملفات والإعدادات.

  `app` (على `127.0.0.1:3100`)، `backup` (يومي، 14 يوماً). تفاصيل التشغيل: [deploy/README.md](../deploy/README.md).

  التطبيق يعمل كمستخدم `app` (ليس root) ولا توجد ملفات env داخل الصورة.
- **إصلاحات أثناء النشر:**
  - استبعاد `uploads` في rsync كان يطابق `src/lib/uploads` أيضاً — صارت الاستثناءات مثبتة على جذر المشروع.
  - الاتصال بالقاعدة صار عند أول استعلام (البناء داخل Docker لا يملك `DATABASE_URL`).
  - السكربت يتوقف عند أي خطأ في البناء.
- **اختُبر:** فحص الصحة، المنيو عبر SSH tunnel، كتابة الصور، نسخة احتياطية فعلية، إعادة تشغيل `app` و `db` (عاد خلال 4 ثوانٍ)،
  وسياسة `unless-stopped` + Docker مفعّل عند الإقلاع. الاستهلاك: التطبيق ~60MB، القاعدة ~38MB.
- **لم يُختبر:** الدخول على نسخة السيرفر — كلمات المرور المولّدة هناك حقيقية ولم أقرأها.

**تنبيه:** لا تدمج هذه الفروع في `main` قبل M8 — Vercel ينشر `main` تلقائياً، والكود الجديد لا يعمل بدون `DATABASE_URL`.
